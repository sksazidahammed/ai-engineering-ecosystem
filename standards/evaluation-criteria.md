# Evaluation Criteria

**Criteria version:** 1.0  
**Last updated:** 2026-11-12 17:39 IST (UTC+05:30)

Verification and evaluation are separate. A project can have a verified identity but still be unsuitable for a particular workflow.

Assess each project across the following dimensions when enough evidence is available:

| Dimension | Questions |
|---|---|
| Usefulness | Does it solve a real, clearly defined problem? |
| Capability | Are the claimed features documented and reproducible? |
| Integration | Which agents, APIs, editors, operating systems, or runtimes does it support? |
| Reliability | Are releases, tests, documentation, and issue handling adequate? |
| Maintenance | Is there credible recent maintenance or an explicit maintenance policy? |
| Security | What permissions, credentials, network access, and execution privileges are required? |
| Privacy | What data leaves the local environment, and where is it processed or retained? |
| Cost | Does it require paid APIs, hosted services, or significant compute? |
| License | Are code, model, dataset, and output terms clear and compatible with intended use? |
| Setup effort | Can a developer install, configure, and remove it predictably? |

## Recommendation labels

Use concise editorial labels only when supported by evidence:

- **High priority:** Strong practical value and a sufficiently understood risk profile.
- **Worth testing:** Promising use case, but hands-on validation or integration testing remains.
- **Specialized:** Useful for a narrower workflow or technical audience.
- **Experimental:** Early-stage, unstable, or dependent on experimental integrations.
- **Not recommended:** Material security, maintenance, licensing, or reliability concerns.

Do not publish numeric scores until a consistent scoring rubric and evidence base exist. Avoid ranking projects solely by stars, downloads, social attention, or README claims.
